# 语音助手项目 · 简历包装与面试素材

> 本文档只整理可复用的表达素材，不再扩展功能。数据均来自本机实测（2026-11-19）。
> 涉及"识别准确率"的地方只写自测结论，不做未经验证的量化宣称。

## 0. 一句话介绍

> 一个全本地、零外网依赖的语音问答系统，链路为 麦克风 → ASR → LLM → TTS → 扬声器，
> 用 FastAPI 服务化，端到端热路径约 1.7 秒。

## 1. 简历条目

### 版本 A：AI 应用 / LLM 工程方向

- 独立完成全本地语音问答系统（ASR → LLM → TTS），基于 FunASR paraformer 离线 ONNX、
  Ollama（qwen2.5:1.5B）与 Windows SAPI5，全链路离线运行，端到端热路径延迟 1.73s。
- 使用 FastAPI 封装 4 个服务接口（健康检查、文字问答、语音问答、语音合成），
  将阻塞式推理放入线程池，上传音频按格式校验并在请求结束后自动清理临时文件。
- 定位并修复语音识别全量乱码缺陷：确认 流式（online）模型 与 离线推理类 输入结构不兼容，
  切换离线模型并修正模型路径匹配逻辑（原逻辑因只比较末级目录名而失效）。
- 设计噪声输入兜底：基于字符重复率过滤 ASR 幻觉文本，并为 LLM 增加生成长度上限，
  将异常输入导致的请求耗时从超时（>120s）降至秒级返回。

### 版本 B：嵌入式 + AI / 端侧方向

- 在普通 PC 上完成端侧语音交互原型验证：ASR 模型 227MB（量化 ONNX），
  与 1.5B 参数本地大模型共存运行，验证了端侧算力的可行性边界。
- 按层解耦 ASR / LLM / TTS 三层，每层保留 mock 与真实两套实现，便于替换与降级。
- 通过推理实例缓存将 ASR 单次耗时从 6.04s（含加载）降至 0.06s（模型常驻）。
- 输出架构文档、部署说明与交付报告，具备从开发到部署的完整闭环经验。

## 2. STAR 讲法

### 90 秒版

**S 背景**：想验证一件事——不依赖云服务，普通 PC 能不能跑完"听 → 想 → 说"的完整语音交互。

**T 目标**：做一个可演示、可服务化的本地语音助手，三层各自可替换。

**A 行动**：拆成三层分别实现。ASR 用 FunASR paraformer 离线 ONNX 模型，一行加载；
LLM 用本地 Ollama，并用 Modelfile 固化机械电子领域的 system prompt；
TTS 用 Windows 自带的 SAPI5，避免再下载模型。之后用 FastAPI 把能力暴露成接口，
用线程池隔离阻塞调用，最后补上噪声兜底和生成上限。

**R 结果**：四个接口全部通过，热路径 1.73 秒，全程不联网。
过程中最大的收获是一个排障：识别结果长期是乱码，最后定位到是下载了流式模型却用离线类加载，
换模型后立刻正常——这让我以后会先核对模型与推理框架的匹配关系，而不是先调参数。

### 3 分钟版补充

- 补充"为什么这么选"：本地部署是为了隐私与离线可用；1.5B 是为了在 CPU 上可用；SAPI 是为了零额外下载。
- 补充"怎么验证"：先分层单测（TTS 出 wav、ASR 出文本、LLM 出回答），再整体联调，最后用接口测。
- 补充"哪里还能更好"：真人语音未做系统评测、ASR 不支持流式、无鉴权，这些都在报告里列了。

| ASR 热推理 | 0.06 s | 模型常驻内存 |
| LLM 回答 | 2.5 – 5.2 s | qwen2.5:1.5B，CPU，回答 267 字 |

## 4. 架构与关键决策

```
麦克风/wav ─▶ ASR(funasr-onnx) ─▶ 文本 ─▶ LLM(Ollama) ─▶ 文本 ─▶ TTS(SAPI5) ─▶ wav/扬声器
                                     ▲
                              FastAPI 服务层（/health /chat /voice /tts）
```

| 决策 | 选择 | 理由 | 代价 |
|---|---|---|---|
| ASR 框架 | funasr-onnx | 原生兼容 FunASR ONNX，pip 一次装完 | 只支持 FunASR 系模型 |
| ASR 模型 | paraformer 离线量化版 | 中文效果好、体积可控 | 227MB、冷启动 6s |
| LLM | Ollama + qwen2.5:1.5B | 本地、CPU 可跑、可定制 Modelfile | 复杂问题深度有限 |
| TTS | pyttsx3 + SAPI5 | 零模型下载、秒级可用 | 音色单一、依赖 Windows |
| 服务层 | FastAPI + 线程池 | 阻塞推理不卡事件循环 | 单机单进程，未做并发优化 |
| 音频格式 | 16kHz 单声道 wav | ASR 模型输入要求 | 需前端转码或录音直出 |

## 5. 五个真实排障记录

### 5.1 ASR 输出全量乱码

- **现象**：任何音频都输出重复乱码，例如 `春侣熏熏熏柤柤剽瀍戒…`
- **定位**：模型目录名含 `-online`，而代码用的是离线推理类 `Paraformer`，输入结构不匹配。
- **修复**：改用离线模型 `…-vocab8404-onnx`，识别立即正确。
- **收获**：先核对"模型类型 ↔ 推理框架"是否匹配，再怀疑参数。

### 5.2 换模型后仍加载旧模型

- **现象**：已下载离线模型，程序仍选中 online 版本。
- **定位**：过滤条件写成 `Path(p).name`，而快照目录名是 `master` / `v2.0.4`，不含 online，条件从未生效。
- **修复**：改为对完整路径判断。
- **收获**：路径类判断要明确比较的是哪一层，最好打印实际选中的路径。

### 5.3 静音导致请求卡两分钟

- **现象**：麦克风录到环境噪声，请求 120 秒超时。
- **定位**：ASR 对噪声幻觉出高重复文本，LLM 对无意义输入长生成，CPU 被打满。
- **修复**：`clean_asr_text()` 按字符重复率过滤；LLM 增加 `num_predict=512`。
- **收获**：语音系统必须假设输入可能是噪声，兜底要在进入 LLM 之前。

### 5.4 localhost 连不上、curl 能连

- **现象**：Python `requests` 连 `localhost:11434` 失败，curl 正常。
- **定位**：`localhost` 优先解析为 IPv6 `::1`，而 Ollama 只监听 IPv4。
- **修复**：统一改为 `127.0.0.1`。
- **收获**：本机服务调试优先用显式 IPv4。

### 5.5 Ollama 启动后端口消失

- **现象**：`/api/tags` 可用，但 `/api/chat` 后进程从端口消失。
- **定位**：多个 Ollama 进程抢占同一端口，bind 失败。
- **修复**：清理残留进程后干净启动。
- **收获**：服务"能连上一次就挂"通常是端口或进程冲突，而不是接口逻辑问题。

## 6. 高频面试 Q&A

### 架构

**Q1：为什么做本地部署，不直接调云 API？**
隐私（语音数据不出本机）、离线可用、零调用成本。代价是模型规模受限、需要自己处理性能与部署。

**Q2：三层怎么拆的，各层职责？**
ASR 只负责音频转文本；LLM 只负责文本问答；TTS 只负责文本转音频。每层都有 mock 实现，
可以单独替换或降级，联调时能快速定位是哪一层的问题。

**Q3：为什么把同步推理放进线程池？**
FastAPI 的 async 端点里调用 requests 或 ONNX 推理会阻塞事件循环，导致其他请求全部排队。
用 `run_in_threadpool` 把阻塞调用丢到工作线程。

**Q4：单条链路怎么做容错的？**
三层各自 try/except 转成明确的 HTTP 状态码；ASR 空结果返回 422 而不是继续调 LLM；
TTS 失败不影响已生成的文本回答。

### ASR

**Q5：为什么选 FunASR paraformer，不用 Whisper？**
paraformer 中文场景成熟、有官方量化 ONNX、体积 227MB 适合端侧；funasr-onnx 封装加载简单。
Whisper 在同体积下中文效果与部署便利性没有明显优势。

**Q6：online 和 offline 模型区别？**
online 是流式模型，输入按 chunk 组织并携带上下文状态；offline 是整段推理。
用错会导致特征错位、输出乱码。流式的好处是低延迟，代价是实现复杂。

**Q7：ASR 冷启动 6 秒怎么优化？**
当前已做实例缓存（热 0.06s）。进一步可做：服务启动时预热、常驻进程、模型转为更小的量化版本。

**Q8：为什么录音要 16kHz 单声道？**
模型训练采样率是 16k；单声道避免混音失真。否则需要重采样，额外耗时且可能影响识别。

**Q9：噪声怎么处理？**
基于字符重复率的启发式过滤（单字符占比 >50% 且长度 ≥8 判为无效），
它简单、可解释、零额外模型开销。更严谨的做法是加 VAD（语音活动检测）。

### LLM

**Q10：为什么选 1.5B？**
CPU 可跑、内存可控。实测 267 字回答约 5 秒。更大模型在无 GPU 的机器上体验会明显变差。

**Q11：system prompt 怎么设计的？**
限定身份（机械电子工程师助手）、限定回答范围、规定风格（简洁、必要时分点），
固化在 Modelfile 中，避免每次请求重复传参。

**Q12：多轮上下文怎么管理？**
在客户端维护 history，超过阈值时截断为最近 4 轮（8 条消息），避免上下文无限增长导致推理变慢。

**Q13：num_predict 限制会不会影响回答质量？**
512 token 约 400 字中文，覆盖绝大多数技术问答；主要作用是防止异常输入触发无限长生成。

### TTS

**Q14：为什么用 SAPI5 而不是 ChatTTS？**
SAPI5 是系统自带、零下载、0.36 秒出音频；ChatTTS 效果好但需要额外模型与更多显存/内存。
本项目优先保证闭环可跑，音色质量不是第一目标。

**Q15：中文语音怎么保证？**
遍历系统语音列表，优先选择语言标签含 `zh` 的语音（本机为 Microsoft Huihui），避免默认选到英文音库。

**Q16：合成文件怎么返回和清理？**
生成临时 wav，用 `FileResponse` 返回，并通过 `BackgroundTask` 在响应发送后删除。

### 工程化

**Q17：文件上传怎么处理？**
`UploadFile` 读取为临时文件，校验后缀必须是 `.wav`，处理后 `finally` 删除；空文件直接 400。

**Q18：如果并发上来怎么办？**
当前是单机单进程 + 线程池。可优化为：推理进程池隔离、Ollama 侧并发控制、
ASR 批处理、再加一层请求队列与限流。

**Q19：数据一致性/状态怎么管？**
系统是无状态的：history 由客户端传入，服务端不存储会话，便于水平扩展。

### 部署

**Q20：为什么没做 Docker？**
Ollama 在容器内需要额外透传与资源调优，ONNX 模型 227MB 要挂载。
更合理的方案是 Ollama 留宿主机、只把 API 打镜像；当前阶段优先本地可运行。

**Q21：有什么安全风险？**
无鉴权、无 HTTPS、仅监听内网。对公网暴露前必须加反向代理、身份校验与限流。

**Q22：怎么扩展到局域网？**
已支持 `--host 0.0.0.0`，同一网段可直接访问；移动端需要保证音频为 16k 单声道 wav，
或由前端录音后在服务端转码。

## 7. 可以继续深挖的方向

| 方向 | 价值 | 大致工作量 |
|---|---|---|
| 网页直接录音（MediaRecorder + 转码） | 体验闭环，演示效果最好 | 中 |

| VAD 语音活动检测 | 替代启发式噪声过滤，更稳 | 低 |
| 评测集与准确率 | 把"能用"变成"可量化" | 中 |
| 并发压测与限流 | 体现工程化深度 | 中 |

## 8. 投递建议

- **AI 应用 / LLM 工程岗**：突出版本 A 条目 + Q3、Q10、Q13、Q18，强调服务化与工程兜底。
- **嵌入式 + AI 岗**：突出版本 B 条目 + Q7、Q8、Q20，强调端侧资源约束与分层解耦。
- **算法岗**：本项目偏应用落地，算法深度有限，建议补充 ASR 指标评测后再投。
- 面试时优先讲 5.1（模型选型错误）与 5.3（噪声兜底）两个案例：
  前者体现定位能力，后者体现对真实输入分布的预判。
